### The Real Issue

Infrastructure configs have **state** and **dependencies**:

```
service-a needs port 3000
service-b needs port 3000  ← CONFLICT

service-c depends on service-d
service-d depends on service-c  ← CYCLE

service-e uses 'localhost' locally
service-e needs 'postgres' in Docker  ← DRIFT
```

Most "autogeneration" ignores this context. Result: Port conflicts, dependency hell, production fires.

## Why Level 3 Actually Scales

### The Context Object

```python
type Context struct {
    all_services: []       # Every manifest in system
    port_allocations: {}  # Used vs available
    dependency_graph: {}  # Full service DAG
    network_topology: {}  # How services connect
    secrets: {}          # Environment vars
    previous_configs: {} # For rollback
}
```

Generators use **full system state**, not just one service.

### Example: Port Resolution

```python
def resolve_port(manifest, ctx):
    requested = manifest['port']
    
    # Check if port already used
    if requested in ctx.port_allocations.values():
        # Auto-assign next available
        return find_next_available(ctx.port_allocations)
    
    return requested
```

**Result:** Zero port conflicts. Ever.

### Example: Dependency Resolution

```python
def resolve_deps(manifest, ctx):
    deps = manifest.get('dependencies', [])
    
    # Verify each dependency exists
    for dep in deps:
        if dep not in ctx.all_service_names:
            raise ConfigError(f"Unknown dependency: {dep}")
    
    # Detect cycles
    if has_cycle(deps, ctx.dependency_graph):
        raise ConfigError("Circular dependency detected")
    
    # Return topological order
    return topological_sort(deps, ctx.dependency_graph)
```

**Result:** Dependencies always resolve. Cycles caught early.

## The 5-Step Validation Pipeline

Every config goes through:

| Step | What | Why |
|------|------|-----|
| 1. **Structure** | Validate JSON schema | Catches missing fields early |
| 2. **Resolve** | Ports, deps, names | Prevents conflicts |
| 3. **Generate** | Starlark execution | Creates configs |
| 4. **Verify** | Syntax + semantic check | No broken YAML |

## Technical Deep Dive

### Starlark vs YAML

YAML templates are static:
```yaml
# Can't handle logic
services:
  {{name}}:
    ports: ["{{port}}:{{port}}"]
```

Starlark is code:
```python
# Full logic, context, validation
def generate(manifest, ctx):
    if manifest['type'] == 'api':
        return api_config(manifest, ctx)
    elif manifest['type'] == 'web':
        return web_config(manifest, ctx)
    else:
        raise ConfigError(f"Unknown type: {manifest['type']}")
```

**Benefit:** Expressive power of Python. Sandboxed execution.

### Auto-Discovery

```python
# Scan filesystem for service.json files
def discover_services(root_path):
    services = []
    for path in walk(root_path):
        if exists(join(path, 'service.json')):
            manifest = load_json(join(path, 'service.json'))
            services.append({
                'path': path,
                'manifest': manifest
            })
    return services
```

**Result:** Drop a `service.json` anywhere. Platform finds it automatically.

### Hot Reload

```python
# Watch for changes
def watch_and_regenerate(resource_path):
    watch([resource_path + '/service.json'])
    
    on_change:
        manifest = load_json(resource_path + '/service.json')
        configs = generate_for_manifest(manifest, get_context())
        atomic_write(configs)
        reload_dependent_services(manifest)
```

**Result:** Change port in `service.json`. All configs update. No restart.
