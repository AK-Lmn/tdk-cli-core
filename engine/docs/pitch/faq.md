# Frequently Asked Questions

## General

### What is the Manifest-Driven Development Platform?

A system where you write one `service.json` file per service, and the platform generates all infrastructure configs automatically—Docker Compose, Nginx, Vite, environment variables—validated, conflict-free, and production-ready.

### How is this different from Docker Compose?

Docker Compose is manual configuration. This platform **generates** Docker Compose (and other configs) from a single source of truth. One manifest → Many configs. Zero drift.

### How is this different from Kubernetes/Helm?

Kubernetes is an orchestration platform. This is a **development** platform that generates infrastructure configs. You can use both: this for local dev, Kubernetes for production.

### Is this a replacement for Tilt/Garden/Skaffold?

**No.** We built **on top of** Tilt. Tilt handles orchestration and live reload. We added the intelligent autogeneration layer.

- **Tilt:** Orchestration + hot reload ✅
- **Our platform:** Config generation + validation ✅
- **Together:** Level 3 autogeneration ✅

## Technical

### Why Starlark and not Python/YAML?

| Language | Pros | Cons |
|----------|------|------|
| **YAML** | Simple | No logic, static only |
| **Python** | Full language | Security risk, non-deterministic |
| **Starlark** | Python-like, sandboxed | Newer (but proven in Bazel/Tilt) |

Starlark gives us the expressiveness of Python with safety and determinism.

### Does this work without Kubernetes?

**Yes!** We built this for Docker Compose first. Kubernetes support is coming, but not required.

### What about existing projects?

Migration is incremental:
1. Install platform
2. Create `service.json` for one service
3. Platform generates configs
4. Gradually migrate other services
5. Remove old manual configs

### How does hot reload work?

1. Platform watches `service.json` files
2. Detects changes
3. Regenerates all configs
4. Tilt applies changes
5. Service restarts (if needed)

**Time:** 1-2 seconds. **Manual steps:** 0.

### What if I need custom logic?

Extend the Starlark generators:

```python
def generate_custom_config(manifest, ctx):
    # Your custom logic here
    return custom_config
```

Full programming language. Any complexity.

## Usage

### Do I need to learn Starlark?

**No.** You write JSON (`service.json`). The platform handles Starlark.

Only if you want to customize generators do you touch Starlark.

### Can AI write the service.json?

**Yes!** In fact, that's the workflow:
1. AI generates code
2. AI (or you) writes simple `service.json`
3. Platform generates infrastructure

**Result:** AI writes features, platform writes configs. No mess.

### What about secrets?

```json
{
  "environment": {
    "DATABASE_PASSWORD": "${secrets:db_password}"
  }
}
```

Actual values from:
- `.env.local` (development, gitignored)
- Infisical/1Password (production)

Platform never stores secret values.

### How do I add a database?

```json
{
  "dependencies": ["postgres"]
}
```

Platform automatically:
1. Adds Postgres to Docker Compose
2. Sets `DATABASE_URL` environment variable
3. Creates database on first run
4. Handles migrations

## Troubleshooting

### "Port already in use"

**Fix:** Use `"port": 0` for auto-assignment.

```json
{
  "port": 0  // Platform finds available port
}
```

### "Dependency not found"

**Fix:** Check the dependency exists:

```bash
ls services/the-dependency/service.json
```

### "Config not regenerating"

**Fix:** Trigger manually:

```bash
tilt trigger <service-name>-config-gen
```

### "Service won't start"

**Debug:**

```bash
# Check logs
tilt logs <service-name>

# Verify generated config
cat autogenerated/docker-compose.<service>.yml

# Test manually
docker-compose -f autogenerated/docker-compose.<service>.yml up
```
