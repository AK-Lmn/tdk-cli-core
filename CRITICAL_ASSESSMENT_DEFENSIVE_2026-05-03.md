## High Confidence - Remove

### 1. `services.ts` - Resource parsing error swallowing (Lines 98-103)
**Current Code:**
```typescript
for (const path of serviceJsonPaths) {
  try {
    resources.push(parseResource(path));
  } catch (err: unknown) {
    console.warn(`Warning: Failed to parse service.json at ${path}: ${getErrorMessage(err)}`);
  }
}
```

**Analysis:**  
This catch block silently swallows ALL parsing errors and continues. If a `service.json` file is malformed, the user gets a warning buried in console output but the command continues as if everything is fine. This masks configuration errors.

**Problem:**
- Only logs a warning, doesn't fail
- User might not see the warning in verbose output
- Corrupted configs are silently ignored

**Recommended Action:** Remove try-catch, let errors propagate. Invalid configs should fail fast.

**Confidence:** HIGH

### 2. `services.ts` - Timestamp reading fallback (Lines 215-221)
**Current Code:**
```typescript
let createdAt = new Date().toISOString();
let lastModified = createdAt;
try {
  const stats = statSync(resource.configPath);
  createdAt = stats.mtime.toISOString();
  lastModified = stats.mtime.toISOString();
} catch (err: unknown) {
  console.warn(`Warning: Could not read timestamps for ${resource.configPath}: ${getErrorMessage(err)}`);
}
```

**Analysis:**  
If we can't read timestamps for a file we just found, something is seriously wrong (race condition, permissions, file system corruption). Using "now" as a fallback masks the real problem.

**Problem:**
- Fake timestamps hide file system issues
- If stat fails after readdir succeeded, we have a race condition or corruption
- Fallback timestamps are misleading

**Recommended Action:** Remove try-catch. If stat fails, the error should propagate.

**Confidence:** HIGH

### 3. `services.ts` - Autogenerated file reading (Lines 266-283)
**Current Code:**
```typescript
try {
  const stats = statSync(filePath);
  const content = readFileSync(filePath, 'utf-8');
  files.push({...});
} catch (err: unknown) {
  const errorCode = isNodeError(err) ? err.code : undefined;
  if (errorCode !== 'ENOENT' && errorCode !== 'EACCES') {
    console.warn(`Warning: Could not read file ${filePath}: ${getErrorMessage(err)}`);
  }
}
```

**Analysis:**  
The file existence is checked with `existsSync()` before this block. If existsSync returns true but read fails, we have a real problem (permissions, race condition). Silently ignoring EACCES is hiding permission issues.

**Problem:**
- Already checked existsSync, so ENOENT shouldn't happen unless race condition
- EACCES (permission denied) is silently ignored - this is a real problem
- If we can't read an autogenerated file that exists, something is wrong

**Recommended Action:** Remove try-catch. Let permission/race errors propagate.

**Confidence:** HIGH

### 5. `services.ts` - Directory traversal error filtering (Lines 48-53)
**Current Code:**
```typescript
try {
  const entries = readdirSync(dir, { withFileTypes: true });
  // ... process entries
} catch (err: unknown) {
  const errorCode = isNodeError(err) ? err.code : undefined;
  if (errorCode !== 'ENOENT') {
    console.warn(`Warning: Could not read directory ${dir}: ${getErrorMessage(err)}`);
  }
}
```

**Analysis:**  
In `findServiceJsonFiles`, ENOENT is filtered out. But ENOENT during a recursive directory scan means a directory disappeared between listing and reading (race condition) or a symlink points to a deleted directory. These are real issues.

**Problem:**
- Race conditions during directory traversal are silently ignored
- Broken symlinks are silently skipped
- Permission errors (EACCES) are only warnings

**Recommended Action:** Remove the ENOENT filter. All directory read errors should be reported.  
**Alternative:** If this is meant to handle "directory was deleted during scan", that should be an explicit comment with proper handling, not silent ignore.

**Confidence:** HIGH

### 6. `resource.ts` - Default port assignment fallback (Lines 466-480)
**Current Code:**
```typescript
let assignedPort: number;

for (let port = portRange.base; port <= portRange.max; port++) {
  if (!usedPorts.has(port)) {
    assignedPort = port;
    break;
  }
}

if (!assignedPort!) {
  console.error(chalk.red(`Error: No available ports in range ${portRange.base}-${portRange.max}`));
  console.error(chalk.gray('Check TILT_RESOURCE_DEFAULTS.star for port configuration'));
  process.exit(1);
}
```

**Analysis:**  
This isn't exactly defensive programming, but uses the non-null assertion operator (`!`) in a confusing way. The check `if (!assignedPort!)` with the `!` operator is defensive - it's handling the case where the loop didn't assign a value.

**Problem:**
- Uses non-null assertion `assignedPort!` which tells TypeScript "trust me, it's not null"
- Then immediately checks if it's falsy
- The `!` after `assignedPort` is unnecessary and confusing

**Recommended Action:** Remove the `!` assertion. Use proper initialization or `| undefined` type.

**Confidence:** HIGH

### 7. `upgrade.ts` - Version reading fallback (Lines 54-63)
**Current Code:**
```typescript
function getCurrentVersion(): string {
  try {
    const packagePath = resolve(...);
    const pkg = JSON.parse(readFileSync(packagePath, 'utf-8'));
    return pkg.version || 'unknown';
  } catch (err: unknown) {
    logVerbose('Could not read package.json', err);
    return 'unknown';
  }
}
```

**Analysis:**  
This is for displaying version info in the upgrade command. Returning 'unknown' is reasonable UX, but it could also fail fast since this is reading the CLI's own package.json which should always exist.

**Trade-off:** UX-friendly vs fail-fast  
**Recommended Action:** Could go either way. For a CLI tool, failing fast if it can't read its own package.json might be better.

**Confidence:** MEDIUM

  action: () => Promise<T>,
  options?: { verbose?: boolean }

**Current usage:** Mostly at command entry points, which is appropriate.

**Recommended Action:** KEEP, but document that this should only be used at command boundaries.

### 10. `tilt.ts` - Port check error swallowing (Lines 8-17)
**Current Code:**
```typescript
export function isPortAvailable(port: number): Promise<boolean> {
  return new Promise((resolve) => {
    const server = createConnection({ port, host: '127.0.0.1' }, () => {
      server.destroy();
      resolve(false);
    });

    server.on('error', () => {
      resolve(true);
    });
  });
}
```

**Analysis:**  
The error handler doesn't distinguish between "port in use" (ECONNREFUSED means available) and actual errors (network down, invalid port). However, for port availability checking, any error typically means "can't connect" which means "port is available."

**Problem:**
- Swallows all errors indiscriminately
- Could mask actual network issues

**Recommended Action:** Review if we need to distinguish ECONNREFUSED (port available) from other errors. Currently appropriate but could be more precise.

**Confidence:** MEDIUM
