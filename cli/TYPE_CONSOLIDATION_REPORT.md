## 2. Duplicates and Near-Duplicates Identified

### Issue 1: Duplicate `ValidResourceType` (RESOLVED ✅)

**Location:** `src/commands/resource.ts` lines 343

**Problem:** Local type defined as:
```typescript
type ValidResourceType = 'backend' | 'frontend' | 'worker';
```

This duplicates the intent of `ResourceType` but with a subset of values.

**Resolution:** 
- Created `CreatableResourceType` as a module-local type alias for the constrained subset
- Used type assertions where the broader `ResourceType` flows into the constrained context
- This is intentional - the resource command only supports creating 3 of the 6 resource types

### Issue 2: Inline `{ label: string; value: string }` (RESOLVED ✅)

**Location:** `src/commands/ui.tsx` line 275

**Problem:** Function parameter typed inline:
```typescript
const handleSelect = useCallback((item: { label: string; value: string }) => {
```

**Resolution:** Replaced with shared `SelectItem` type:
```typescript
const handleSelect = useCallback((item: SelectItem) => {
```

### Issue 3: Local `StatusValue` (RESOLVED ✅)

**Location:** `src/utils/formatting.ts` line 3

**Problem:** Local type definition:
```typescript
type StatusValue = string | undefined;
```

**Resolution:** 
- Consolidated into shared `StatusValue` in `src/types/index.ts`:
```typescript
export type StatusValue = ResourceStatus | StackHealthStatus | TiltRuntimeStatus | ServiceUrl['status'] | string | undefined;
```
- Updated `formatting.ts` to import from shared location

## 3. Consolidation Strategy Implemented

### Strategy: "Centralize Shared, Keep Local Specific"

1. **Status Types** → Centralized union in `types/index.ts`
   - All status-related types now share a single source of truth
   - Functions like `getStatusColor()`, `getStatusIcon()` work with all status variants

2. **UI Item Types** → Use shared `SelectItem`
   - List items across all UI components use consistent structure
   - Future additions to item structure only need changes in one place

3. **Resource Type Subsets** → Module-local type aliases
   - When a module needs a constrained subset (e.g., only creatable types), define it locally
   - Document the relationship to the central type with comments

4. **Component Props** → Keep in component files
   - Each React component's props are unique to its needs
   - No duplication detected across components

## 6. Recommendations NOT Implemented (With Reasons)

### Recommendation A: Unify Component Props into Base Interface
**Status:** NOT IMPLEMENTED

**Rationale:** Each component has distinct prop requirements:
- `TabBarProps` needs `onTabChange` callback
- `FileTreeProps` needs `onSelect` with `FileNode` parameter
- `ResourceTableProps` needs `resources` array

Creating a base interface would force artificial commonality and reduce type safety.

---

### Recommendation B: Move ALL Types to `types/index.ts`
**Status:** NOT IMPLEMENTED

**Rationale:** Over-centralization harms maintainability:
- Component props should live with components (cohesion principle)
- Module-internal types should stay module-internal (encapsulation)
- Only truly shared types belong in the central registry

Current organization follows the "where used, where defined" principle appropriately.

---

### Recommendation C: Replace `ResourceType` Union with Enum
**Status:** NOT IMPLEMENTED

**Rationale:** String literal unions are preferred in this codebase:
- They allow direct use in JSON parsing (no enum conversion needed)
- They're more ergonomic for CLI argument parsing
- They're consistent with existing patterns (FileType, ResourceStatus, etc.)

## 8. Conclusion

The TDK CLI type system was already well-organized. The consolidation work focused on:

1. **Eliminating 1 duplicate type definition** (StatusValue)
2. **Replacing 1 inline type** with shared type (SelectItem)
3. **Clarifying type relationships** with better documentation (CreatableResourceType)

**Result:** Cleaner type imports, better type reuse, and no loss of type safety.
