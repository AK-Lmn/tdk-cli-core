## Issues Found

### 1. Missing Exports in Types Index

**FileNode** is exported from `FileTree.tsx` but not re-exported from `types/index.ts`:
```typescript
// FileTree.tsx - line 7
export interface FileNode { ... }

// But NOT in types/index.ts - should add for discoverability
```

### 2. Inconsistent Component Props Pattern

Component prop interfaces are defined locally but could follow a consistent pattern:
- `TooltipProps` → centralized in `types/index.ts` ✅
- `TabBarProps`, `DetailPanelProps`, `ResourceTableProps`, `FileTreeProps` → defined in component files

### 3. Duplicate Type Patterns in Tests

Test file `error-handling.test.ts` defines local interfaces that mirror validation patterns:
```typescript
// Line 109 - local ManifestResult interface
interface ManifestResult { ... }
```

### 4. Missing Type Exports in Component Index

`cli/src/components/index.ts` should re-export component types:
```typescript
// Currently missing from index.ts:
export type { TabId } from './TabBar.js';
export type { FileNode } from './FileTree.js';
```

## Consolidation Recommendations

### HIGH CONFIDENCE (Safe to implement)

1. **Add FileNode to types/index.ts**
   - Risk: None
   - Benefit: Single import source for file tree types
   - Files to update: `types/index.ts`, `FileTree.tsx`

2. **Export ValidationResult pattern**
   - Extract from validation.ts and test files
   - Create shared `ValidationResult<T>` type
   - Risk: Low - additive only

3. **Add CheckResult to types/index.ts**
   - Risk: Low - single source of truth
   - Files: `types/index.ts`, `doctor.ts`

4. **Update component index.ts exports**
   - Risk: None - additive only
   - Add type re-exports for discoverability

### MEDIUM CONFIDENCE (Review required)

5. **Consolidate ServiceUrl**
   - Could be useful for network-related commands
   - Risk: May overlap with future API client types

6. **Standardize Component Props Location**
   - Options:
     a) Keep in component files (current) - fine for internal
     b) Move all to types/index.ts - better for external consumers
   - Decision: Keep in component files, re-export from index.ts

### LOW CONFIDENCE (Defer or reject)

7. **Create ValidationResult generic type**
   - Current pattern: `{ valid: boolean; error?: string }`
   - Could become: `ValidationResult<T>`
   - Risk: Over-engineering for simple cases

8. **Extract all component props to types/index.ts**
   - Risk: Unnecessary indirection for component-only types
   - Recommendation: Reject - keep component props colocated

## Type Naming Conventions Assessment

✅ **Good patterns:**
- PascalCase for interfaces and types
- Descriptive names without redundant suffixes
- Boolean properties use `is-*`, `has-*`, `can-*`, `did-*` prefixes

⚠️ **Inconsistencies:**
- Some component props use `*Props` suffix (standard React pattern) ✅
- Some types use domain prefixes, some don't

## Conclusion

The type system is **well-organized overall**. The centralized `types/index.ts` serves as a good source of truth for domain types. The main improvements needed are:

1. **Minor gaps in exports** (FileNode, CheckResult)
2. **Missing type re-exports** in component index.ts
3. **Consistent documentation** of type patterns in AGENTS.md

No critical issues found. Recommended actions are all low-risk additions that improve maintainability without breaking changes.
