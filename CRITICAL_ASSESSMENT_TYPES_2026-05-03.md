## Issues Found

### Issue #1: Duplicate Status Values (LOW Confidence)

**Current State:**
Multiple status type definitions with overlapping values:

```typescript
// types/index.ts
export type ResourceStatus = 'ready' | 'pending' | 'error' | 'unknown';
export type StackHealthStatus = 'healthy' | 'degraded' | 'error' | 'unknown';
export type TiltRuntimeStatus = 'running' | 'pending' | 'error' | 'unknown';
export type TiltBuildStatus = 'ok' | 'error' | 'in_progress' | 'unknown';
export type ExtendedStatus = 'active' | 'failed' | 'critical' | 'stopped' | 'starting' | 'building' | string;

// formatting.ts
 type StatusCategory = 'success' | 'error' | 'warning' | 'unknown';
```

**Assessment:**
- These are **intentionally separate** - they represent different domain concepts
- `StatusValue` union already provides aggregation when needed
- `StatusCategory` is a presentation-layer categorization, not a domain type
- **Recommendation:** No consolidation needed - current design is correct

### Issue #2: Missing `Tab` Interface Export (MEDIUM Confidence)

**Current State:**
```typescript
// TabBar.tsx lines 6-10
interface Tab {
  id: TabId;
  label: string;
  shortcut: string;
}
```

**Issue:**
- `Tab` interface is used internally but could be useful for consumers
- However, it's an implementation detail of the TabBar component
- The `TABS` array is private to the component

**Recommendation:** **Keep local** - it's a component implementation detail

### Issue #3: Internal JsonValue Support Types (LOW Confidence)

**Current State:**
```typescript
// types/index.ts lines 97-98
interface JsonArray extends Array<JsonValue> {}
interface JsonObject extends Record<string, JsonValue> {}
```

**Issue:**
- These are not exported but support the exported `JsonValue` type
- They're properly scoped as internal implementation details

**Recommendation:** **Keep as-is** - internal helpers don't need export

### Issue #4: Component Props Pattern Inconsistency (LOW Confidence)

**Current State:**
- Some components use `React.FC<Props>` pattern
- Props interfaces are defined locally in each component
- Pattern is consistent across components

**Assessment:**
- This is intentional - props are component-specific
- No benefit to centralizing component prop types
- Violates "co-location" principle

**Recommendation:** **No change needed**
